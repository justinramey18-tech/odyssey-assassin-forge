# Project Architecture Rules

- The default Party home uses a dedicated paused, poster-backed Enter Story video element; other background videos stay with the existing looping background system so their behavior cannot change.
- Dice odds are chosen as a profile (odyssey-dice-odds-profile); rollD20 resolves the mode per roll context via resolveOddsForContext, so one setting can differ between combat and roleplay.
- An overlay that must sit above an open drawer renders inside that drawer's content (inline prop, no body portal) and carries data-vaul-no-drag, because a modal drawer keeps focus and treats outside taps as close — raising its z-index alone cannot win.
- npc-combat carries identical copies of npc-reply's handler/models/repo/prompt in npc-combat/npc-reply/, because each server function deploys only its own folder; a test fails if the copies drift, so re-copy after editing npc-reply.
- Automatic party launch passes an explicit initial Live Table choice through the existing screen chain; drawer state remains locally owned so Return to Story cannot trigger automatic reopening.
- Cache Live Table rows separately from DM narration by account and party; successful server reads replace stale cached rows while in-flight live changes survive, and failed reads must retain the visible conversation.
- Arena Live Table Sparring renders the real PartyDMScreen through runtimeOverrides with local Arena hooks; never rebuild a separate mock table, because a second copy drifts from the live game.
- Party Sparring runs on the host's phone and is shared over a live broadcast channel (no database rows); members mirror the host's fight and send actions to it, because campaign tables and the fight referee must never see practice fights.
- Campaign Map world geography lives in ai_dm_campaigns.map_state with all math in src/lib/campaign-map.ts; never reuse the combat map_markers state, because tactical positioning and world travel have different rules.
- Custom companions are drawn in code on a canvas (src/components/companion/CompanionCanvas.tsx) from the saved look in src/lib/companion-rig.ts; never ship per-look image files, because every look must stay customizable and tiny to save.
- Nested campaign maps are one versioned atlas envelope (src/lib/campaign-atlas.ts) inside the existing campaign_map row; app saves go only through the write_campaign_atlas compare-and-set call and each edit patches one captured map id, because whole-envelope replays from stale tabs would erase other maps or newer travel. The one exception is authenticated connector area installs, which use the service-role-only bridge_install_campaign_area (contract and recovery in docs/bridge-campaign-install.md; the latest definition is in drizzle/migrations/0030_fix_bridge_install_guide_alias_apply.sql) with the same lock + expected-version checks, because a connector must not impersonate the host.
- City-scale travel is a per-map travelScale flag inside campaign map state (not a new atlas navigation mode), so the server atlas validator and all travel/clock math stay shared; city only lifts the travel-day cap and changes wording.
- Travel Director is service-only: identity hashes PostgreSQL jsonb of destinationLocationId, pace and ordered legs; map_id/totalMiles are checked separately. Private plan/sync commits lock events/map; firing uses leases and atomic complete_travel_event_post to prevent stale plans and duplicate posts. Offline events reuse QStash, never a new scheduler.
- Party signup onboarding runs through party-link onboarding_* actions calling service-role-only onboarding_* database functions (drizzle/migrations/0031_party_onboarding_foundation.sql); a seat and save are created together only at finalize, and a BEFORE INSERT guard on party_members enforces the seat limit and one active party for every join path, because separate client checks race.
- Party creation context is built only server-side in supabase/functions/_shared/party-creation-context.ts (host party guides + dm_session summary + read-only atlas-path area guides, secret markers stripped, one bounded extraction call, lease-coalesced cache keyed by source fingerprint); the creator's partyCreationSessionId branch receives only that projection, because raw GM material must never reach the browser or the chat model.
- Party signup hand-off builds the new save only in the pure src/lib/ai-creation/party-build-save.ts (session-derived IDs, explicit scoped keys, never the active hero's state) and opens play through a one-shot account-level receipt that Index re-verifies with onboarding_resume before loading that exact save, because generic restore/pending-AI paths would otherwise load or overwrite the wrong character.

- Live Table speech artwork uses nine-slice borders and a separate tail above naturally sized portraits, because stretching a whole frame distorts corners and crops speakers.
- Buffs use optional manual metadata validated in spellResolve; homebrew edits spread original fields to avoid data loss.
